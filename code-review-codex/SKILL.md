# code-review 代码审查

对当前分支 diff（或指定 PR/分支/路径目标）进行多角度代码审查，输出高信号缺陷与清理项。分四个级别：low / medium / high / xhigh。级别越低越保守（少而精），越高越追求召回（宁可多报，经独立验证过滤误报）。

## 用法

```
/code-review [<level>] [<target>]
```

- `<level>`：`low` | `medium` | `high` | `xhigh`（缺省 `medium`）
- `<target>`（可选）：PR 号、分支名、ref 区间、文件路径，或自由指令（如"只审查 src/foo.ts"、"重点关注错误处理"）

## 通用前置（所有级别）

### Phase 0 —— 收集 diff

运行 `git diff @{upstream}...HEAD`（无 upstream 时用 `git diff main...HEAD` / `git diff HEAD~1`）获取被评审的统一 diff。若有未提交改动，或区间 diff 为空，也运行 `git diff HEAD` 并把工作树改动纳入范围——评审常在提交前执行。若传了 target，按 target 缩小范围：PR 号/分支/ref 区间构造对应 diff 命令，路径或自由指令限定审查范围。

**统计改动规模**：用 `git diff --numstat` 统计两个数字——

- `lines`：加删行合计
- `files`：改动文件数

二者驱动后续各级别的候选采集规模与报告上限（见下）。

以该 diff 为评审范围。

**读取评审规则**：读取项目根目录 `REVIEW.md`（存在时）与 CLAUDE.md（用户级 `~/.claude/CLAUDE.md`、仓库根）。二者角色不同：

- **CLAUDE.md**：共享项目说明，Claude Code 所有任务通用，非仅审查。本评审将其作为**项目上下文**读取，新引入的违规标记为小问题（`minor`）。
- **REVIEW.md**：仅审查说明，**直接注入审查管道的每个环节（finder / verifier / sweep）作为最高优先级规则**。可用它改变标记的内容（重点检查/排除某类问题）、严重程度与报告方式——凡与本文档默认规则冲突处，以 REVIEW.md 为准。

REVIEW.md 不存在时按本文档默认规则执行。

### 报告输出格式（通用，不依赖宿主工具）

评审结果按统一结构输出，可被脚本、CI 或任何平台直接消费。**主输出为 JSON 数组**，同时附 Markdown 行式清单给人读。

**JSON 数组（机器可读，主输出）**：

```json
[
  {
    "file": "path/to/file.ext",
    "line": 123,
    "summary": "单句缺陷陈述",
    "short_summary": "≤60 字符压缩论断",
    "failure_scenario": "具体输入/状态 → 错误输出/崩溃",
    "category": "correctness",
    "verdict": "CONFIRMED",
    "severity": "main"
  }
]
```

字段说明：

- `file`、`line`：定位，repo 相对路径
- `summary`：单句缺陷陈述
- `short_summary`：≤60 字符压缩论断（用于列表展示）
- `failure_scenario`：具体输入/状态 → 错误输出/崩溃；清理类写具体代价（重复/浪费/难维护/违反哪条规则），而非崩溃
- `category`：kebab-case 标签——`correctness` / `reuse` / `simplification` / `efficiency` / `altitude` / `conventions`
- `verdict`（medium/high/xhigh 验证后）：`CONFIRMED` / `PLAUSIBLE`
- `severity`：`main`（默认）/ `minor`——CLAUDE.md 新引入的违规标记为 `minor`，其余为 `main`

数组按严重度排序（正确性在清理之前，CONFIRMED 在 PLAUSIBLE 之前，`minor` 违规排最后）。无问题输出 `[]`，绝不硬凑。

**Markdown 报告模板（人读，紧随 JSON 输出）**：每次执行严格按以下固定骨架输出，保证报告格式确定：

```markdown
# 代码审查报告

| 项目     | 值                                                             |
| -------- | -------------------------------------------------------------- |
| 级别     | medium                                                         |
| 评审范围 | @{upstream}...HEAD                                             |
| 改动规模 | 12 个文件 / 845 行                                             |
| 统计     | 8 角度 · 23 候选 · 保留 8（CONFIRMED 5 / PLAUSIBLE 3）· 否决 5 |

## 发现

### 1. src/foo.ts:123 — CONFIRMED（correctness）

**摘要**：...

**失败场景**：...

### 2. src/bar.ts:45 — PLAUSIBLE（conventions, minor）

**摘要**：...

**失败场景**：...
```

模板字段规则：

- `评审范围`：diff 来源（分支/ref/PR）；传了 target 时写 target
- `改动规模`：`<files> 个文件 / <lines> 行`
- `统计`：`<角度数> 角度 · <候选数> 候选 · 保留 <n>（CONFIRMED <n> / PLAUSIBLE <n>）· 否决 <n>`；low 档无验证环节写"无验证"
- `发现`：编号从 1 起，顺序与 JSON 数组一致（严重优先）；每条含定位、verdict、category、单句摘要、具体失败场景；`minor` 违规在 category 后加注 `minor` 且排最后
- 空报告：`发现` 下写"未发现可上报的问题"，绝不硬凑
- 字段缺省写 `—`，骨架不省略、顺序不调整

**落盘（可选）**：若环境允许，将结果写入 `code-review-report-[评审时间戳].json` 与 `code-review-report-[评审时间戳].md`（同上模板），供下游流程引用。

## 级别定义

级别区分的本质是**执行架构与判定偏向**（为"抓全"付出多少成本、容忍多少误报），报告上限只是这种权衡的自然结果，非级别定义本身。

### 级别差异

| 维度     | low                                        | medium                                        | high                           | xhigh                                |
| -------- | ------------------------------------------ | --------------------------------------------- | ------------------------------ | ------------------------------------ |
| 执行架构 | 单遍内联：1 次读 diff                      | 顺序执行：主 agent 按 8 角度顺序采集候选      | 同 medium（8 角度）            | 同 medium，10 角度 + 主 agent 补漏 sweep |
| 验证环节 | 无独立验证，自我审查即最终                 | 1 票 3 态验证（precision 从严）               | 1 票 3 态验证（recall 偏向）   | 1 票 3 态验证（recall 偏向）         |
| 审查面   | 仅正确性：hunk 内 + 外围函数，跳过测试改动 | 8 角度（正确性 5 + 清理 3 + 海拔 + 规范）全量 | 同 medium                      | 10 角度（含海拔与规范）全量          |
| 报信标准 | 只报最确凿（hunk 可见的运行时 bug）        | 每条都应是维护者会行动的问题                  | 宁可多报，漏报比误报更不可接受 | 同 high                              |
| 成本     | 最低：1 次 diff 读取                       | 中：8 角度 + N 候选自验证                     | 中                             | 高：+1 sweep                         |

### 规模驱动的动态上限（通用规则）

上限不设死值，按 diff 规模缩放——**每约 150 行改动 ≈ 1 个值得上报的问题配额**（`⌈lines/150⌉`）：

| 级别   | 报告上限（cap）                 | 候选采集（每角度）          |
| ------ | ------------------------------- | --------------------------- |
| low    | `max(4, min(⌈lines/150⌉, 8))`   | —                           |
| medium | `max(8, min(⌈lines/150⌉, 15))`  | `clamp(⌈lines/250⌉, 6, 10)` |
| high   | `max(10, min(⌈lines/150⌉, 20))` | `clamp(⌈lines/200⌉, 6, 12)` |
| xhigh  | `max(15, min(⌈lines/150⌉, 25))` | `clamp(⌈lines/200⌉, 8, 14)` |

- `⌈lines/150⌉` 例：50 行 → 各档保底 4/8/10/15；800 行 → 6/8/10/15 起；2000 行 → medium 上限 14、xhigh 保底 15；超大 diff 触及封顶 8/15/20/25
- 改动文件多但每文件改动少时，low 档另有下限目标 `min(files, 4)`（见下）
- **候选采集与验证不设上限**：候选全量过验证，报告上限只在最终排序时砍尾；超上限只砍最不严重者，容量未满一条不丢
- **升级提示**：`lines > 500` 时在报告开头建议"改动规模大，high/xhigh 档更合适"

### low —— 单遍内联，无验证，只报最确凿

**Turn 1 读**：一次工具调用读统一 diff。跳过 test/fixture hunk（`test/`、`spec/`、`__tests__/`、`*_test.*`、`*.test.*`、`fixtures/`、`testdata/`）——本级别不审查测试文件改动。不全文件读取。

**Turn 2 报**：只报 hunk 内可见的运行时正确性 bug：

- 颠倒/错误的条件、off-by-one
- null/undefined 解引用（相邻行显示值可能缺失）
- 缺失的 `await`
- falsy-zero 检查
- 错变量复制粘贴
- catch 中吞掉的、本应传播的错误
- 被删的 guard
- 新代码重复了 diff 上下文里可见的现有 helper
- diff 遗留的死代码

**不报**：风格、命名、性能、缺测试、hunk 外的任何东西。

**输出**：最多 `max(4, min(⌈lines/150⌉, 8))` 条，严重优先。目标下限 `min(files, 4)`——改动文件越多，至少报的条数越多；若不够，对最大的改动文件和任何**被删除**的代码块再补一遍，仍不够则如实报已有条数。空数组仅限 diff 确无问题。

### medium —— 主 agent 顺序执行 + 独立验证（precision 从严）

**目标**：精确性——每条 finding 都应是维护者会去处理的那种。

**Phase 1 找候选**：主 agent 在本上下文中按 A–H 顺序逐一执行 8 个 finder 角度（角度全文见下节），每角度至多 `clamp(⌈lines/250⌉, 6, 10)` 条候选，每条含 `file`、`line`、一行 `summary`、具体 `failure_scenario`。改动越大单角度候选越多，候选总量无上限。**不启动任何子代理，全部在主 agent 上下文中顺序完成**。

把所有带可命名失败场景的候选都保留下来——悄悄丢弃半信半疑候选是漏报主因。

**Phase 2 验证（1 票 3 态）**：主 agent 切换为"验证人"视角，对去重后的每条候选独立裁决（对比 diff + 相关文件 + 候选），判词：

- **CONFIRMED**——能指出触发它的输入/状态以及错误输出或崩溃，引用该行
- **PLAUSIBLE**——机制真实、触发不确定（时序、环境、配置），说明什么能证实它
- **REFUTED**——事实错误（代码并非如此）或在别处已有 guard，引用证明行

保留 CONFIRMED 与 PLAUSIBLE。没有给出判词的候选直接丢弃，绝不伪造 PLAUSIBLE。

**输出**：最多 `max(8, min(⌈lines/150⌉, 15))` 条，严重优先。验证幸存者超过上限才砍尾，容量未满一条不丢。

### high —— 召回偏向验证

**目标**：召回——抓住细心审查者一次能抓到的所有真实 bug。漏报比误报更不可接受，宁可多报。

**Phase 1 找候选**：同 medium 的 8 角度，每角度至多 `clamp(⌈lines/200⌉, 6, 12)` 条候选——级别越高单角度采集越宽，候选总量无上限。

**Phase 2 验证（召回偏向）**：**PLAUSIBLE 默认**——不得以"纯属推测""依赖运行时状态"为由否决候选，当状态真实可达时：并发竞争、罕见路径上的 nil（错误处理、冷缓存、缺可选字段）、falsy-zero 当缺失、代码未排除的边界 off-by-one、重试风暴/部分失败、丢失锚点的 regex/白名单，均为 PLAUSIBLE。REFUTED 仅限能从代码构造反证：事实错误（引用实际行）、可证明不可能（类型/常量/不变量）、本 diff 已处理（引用 guard）、无观测效果纯风格。

**输出**：最多 `max(10, min(⌈lines/150⌉, 20))` 条，严重优先。验证幸存者超过上限才砍尾，容量未满一条不丢。

### xhigh —— 10 角度 + 召回偏向验证 + 补漏 sweep

**目标**：最大召回——不遗余力抓所有真实 bug，sweep 兜底第一遍漏掉的。

**Phase 1 找候选**：主 agent 在本上下文中按顺序逐一执行同 medium 的 8 finder 角度 + 海拔 + 规范共 10 角度（全文见下节），每角度至多 `clamp(⌈lines/200⌉, 8, 14)` 条候选，候选总量无上限。**不启动任何子代理，全部在主 agent 上下文中顺序完成**。

**Phase 2 验证（召回偏向）**：同 high——PLAUSIBLE 默认，不得以"纯属推测"为由否决候选；REFUTED 仅限能从代码构造反证。

**Phase 3 补漏 sweep**：主 agent 切换为"全新 reviewer"视角，拿着已确认清单再读一遍 diff 与外围函数，只找清单外的缺陷，不重新推导已列项。重点：移出/抽取代码丢失的 guard 或锚点；二级坑（可变默认参数只求值一次、`hash()` 非确定性、锁作用域缩小、带副作用的谓词方法）；测试 setup/teardown 不对称；配置默认值翻转。最多补 8 条，无新的则空返回。

**输出**：最多 `max(15, min(⌈lines/150⌉, 25))` 条，严重优先。验证幸存者超过上限才砍尾，容量未满一条不丢。

## finder 角度（medium/high/xhigh 共用）

### 正确性（前五个）

**角度 A —— 逐行 diff 扫描**
逐行读每个 hunk，再读每个 hunk 所在的外围函数——被改动函数中未改动行里的 bug 也在范围内（PR 重新暴露了它们或未修复它们）。对每一行问：什么输入、状态、时序或平台会让这一行出错？寻找：颠倒/错误条件、off-by-one、null/undefined 解引用、缺失 `await`、falsy-zero 检查、错变量复制粘贴、catch 吞错、未转义 regex 元字符。

**角度 B —— 删除行为审计**
对 diff 删除或替换的每一行，指出它保证的不变量或行为，然后在新代码中搜索该不变量在哪里被重建。找不到就是候选：被删 guard、丢失错误路径、收窄校验、删掉却曾覆盖真实场景的测试。

**角度 C —— 跨文件追踪**
对改动到的每个函数，Grep 找调用方，检查改动是否破坏调用点：新前置条件、改变返回形态、新异常、时序/顺序依赖。也检查被调方：同批平行改动是否让某次调用变危险。

**角度 D —— 语言陷阱专家**
扫该 diff 语言/框架的经典陷阱：JS falsy-zero、`==` 强转、闭包捕获循环变量；Python 可变默认参数、晚绑定闭包；Go nil-map 写入、range 变量捕获；SQL 注入；时区/DST 漂移；浮点相等。报 diff 引入的实例。

**角度 E —— wrapper/proxy 正确性**
PR 新增/修改包装类（cache、proxy、decorator、adapter）时，检查每个方法是否路由到被包装实例而非绕回 registry/session/global——如持 `delegate` 字段的缓存提供方用 `session.get(...)` 而非 `delegate.get(...)` 解析 ID，会重入缓存或递归。同时检查包装器转发调用方实际用到的全部方法。

### 清理（后三个）

**复用**：标记新代码重复实现了代码库已有的东西——Grep shared/utility 模块和改动相邻文件，指出应改调的现有 helper。

**简化**：标记 diff 增加的不必要复杂度：冗余或可推导状态、轻微变体复制粘贴、深嵌套、遗留死代码。指出能做同样事情的更简形式。

**效率**：标记 diff 引入的浪费：冗余计算/重复 I/O、串行执行的独立操作、加入启动或热路径的阻塞工作。标记由闭包/捕获环境构建的长生命周期对象——整个生命周期持有外围作用域（大值时即内存泄漏）；优先用只复制所需字段的 class/struct。

### 海拔与规范（附加两角）

**海拔（Altitude）**：检查改动是否实现在正确深度，而非脆弱补丁。叠加在共享基础设施上的特例是"修得不够深"的迹象——优先泛化底层机制。

**规范（CLAUDE.md / REVIEW.md）**：两套规则文档，角色不同——

- **CLAUDE.md（项目上下文）**：读取用户级 `~/.claude/CLAUDE.md`、仓库根 CLAUDE.md，以及改动文件任何祖先目录里的 CLAUDE.md / CLAUDE.local.md（目录的 CLAUDE.md 只适用于该目录及以下文件）。逐个体读取，检查 diff 是否**新引入**明确违规。**只有能引用规则原文和违反它的确切行时才标记**——不要风格偏好，不要含糊的"文档精神"推断。finding 中写出 CLAUDE.md 路径并引用规则，`severity` 记为 `minor`，排在所有其他 finding 之后。无适用 CLAUDE.md 则本部分返回空。
- **REVIEW.md（审查指令，最高优先级）**：项目根 `REVIEW.md` 存在时，其规则**高于本文档默认规则**——改变标记什么（要求重点检查某类问题、禁止报某些类别）、严重程度（把某类问题升/降级）、报告方式（要求附链接、特定措辞等）。注入审查管道的每个环节，finders 采集候选时即须遵守；REVIEW.md 未涉及的按本文档默认规则执行。

## 汇总规则

- 清理、海拔、规范候选的 `failure_scenario` 写具体代价（重复了什么、浪费了什么、多难维护、违反了哪条规则），而非崩溃。
- 正确性 bug 永远排在清理/海拔/规范之前；`minor`（CLAUDE.md 违规）排所有 finding 之后。
- 同一根因的合并为一条，附 `[same root cause also at: file:line]`；合并组内任一 CONFIRMED 则整组判 CONFIRMED。
- 容量未满不许静默丢弃：验证幸存者要么作为主条要么作为合并注出现，只有上限满才省略。
- 模板 `统计` 行如实填写：角度数、候选数、验证保留/否决数，与 JSON 数组一致。

## 注意事项

- 不要报：风格、命名、一般性性能问题、缺测试、既有问题（非本次改动引入）、linter 能捕获的问题。
- 不确定是否真实的问题不要报——误报侵蚀信任。
